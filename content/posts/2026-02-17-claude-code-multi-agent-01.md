1인 개발자로 살다 보면 항상 같은 벽에 부딪힌다. **시간이 부족하다.**

개발만 해도 바쁜데, 마케팅도 해야 하고, 블로그 글도 써야 하고, 유튜브 영상도 올려야 한다. 이걸 혼자 다 하면서 본업까지 챙기는 건 물리적으로 불가능에 가깝다.

그래서 생각했다. *AI 에이전트를 직원처럼 쓰면 어떨까?*

## 수익 구조 먼저 설계했다

실행에 앞서 수익 구조를 먼저 명확하게 잡았다. 단기 수익보다 **점진적으로 완성도를 높이며 수익이 불어나는 구조**가 목표다.

수익 채널은 세 가지다:
- 게임 개발 + 인앱 광고
- 기술 블로그 + AdSense
- 유튜브/강좌 + 광고

그리고 핵심 전략은 **하나의 작업 → 세 가지 콘텐츠** 파이프라인이다.

```
게임 기능 하나 개발
  ├→ 블로그 글 (개발 과정 정리)
  ├→ 유튜브 영상 (라이브코딩/해설)
  └→ SNS 홍보 (티저/요약)
```

같은 작업을 세 채널에 배포하면, 콘텐츠 생산 효율이 3배가 된다. 이론적으로는.

## 에이전트 계층 구조를 설계했다

처음에는 에이전트를 평면적으로 나열했다. "개발 에이전트", "블로그 에이전트", "마케팅 에이전트"처럼. 그런데 금방 문제가 보였다. 에이전트들이 서로 어떻게 소통하는지, 누가 우선순위를 정하는지 명확하지 않았다.

실제 조직처럼 **계층 구조**가 필요하다는 결론이 나왔다.

```
            CEO (나)
                 │
       ┌─────────┴──────────┐
       │  경영기획실장 (CoS)   │
       └─────────┬──────────┘
                 │
     ┌───────────┼───────────┐
     ▼           ▼           ▼
  개발실장    홍보실장    마케팅실장
```

**경영기획실장(Chief of Staff)** 에이전트가 핵심이다. 내(CEO)가 "블로그 글 써줘"라고 지시하면, 경영기획실장이 이를 구체적인 실행 계획으로 분해해 각 실장에게 배분한다. 나는 큰 방향만 잡으면 된다.

각 에이전트는 `AGENT.md` 파일로 페르소나와 역할을 정의한다. 성격, 의사결정 원칙, 커뮤니케이션 스타일까지 명시해두면 Claude가 그 역할을 일관성 있게 수행한다.

## 컨텍스트 문제를 해결해야 했다

기술적으로 가장 큰 고민은 **컨텍스트**였다.

모든 에이전트를 한 Claude 세션에서 돌리면 컨텍스트가 금방 한계에 달한다. 에이전트가 많아질수록 서로의 맥락이 뒤섞이고, 응답 품질이 떨어진다.

해결책은 **독립 컨텍스트 + 메시지 패싱**이다.

- 각 에이전트가 별도 Claude Code 세션에서 실행된다
- 에이전트 간 지시와 보고는 외부 채널로 교환한다
- Git 저장소가 공유 상태 저장소 역할을 한다

## 파일 기반 메시지 패싱의 한계

처음에는 `agents/{에이전트}/inbox/`, `agents/{에이전트}/outbox/` 디렉토리를 만들어서 파일로 지시와 보고를 교환했다. 아이디어 자체는 단순하고 우아해 보였다.

그런데 실제로 운영해보니 문제가 드러났다.

**실용적 문제**

- 파일 컨벤션을 일관되게 유지하기 어렵다. 어떤 파일이 "처리된 것"이고 어떤 것이 "대기 중"인지 추적이 힘들다.
- 에이전트 A가 에이전트 B에게 보낸 메시지를 다시 확인하려면 파일 시스템을 직접 뒤져야 한다.
- 완료 여부를 알기 위해 주기적으로 파일을 확인해야 한다 — 즉, 폴링 방식이다.

**전략적 판단 — 왜 GitHub Issues로 전환했나**

세 가지 대안을 검토했다.

1. **파일 기반 유지**: 도구 추가 없이 단순하지만, 추적/조회/알림이 불가능하다
2. **Slack/Discord 봇**: 알림은 좋지만, 별도 인프라 유지 비용이 발생한다. 1인 기업에서 인프라를 늘리는 건 리스크다
3. **GitHub Issues**: 이미 코드 레포가 GitHub에 있고, Issues는 기본 제공이다. 라벨로 라우팅, 댓글로 보고, 닫기로 완료 처리 — 메시지 시스템에 필요한 기능이 모두 있다

결론은 **GitHub Issues**였다. 이유는 세 가지다.

- **인프라 제로 추가**: 이미 쓰고 있는 도구 안에서 해결한다
- **가시성**: 모든 지시와 보고가 Issues에 기록되어 나중에 검색·참조할 수 있다
- **자동화 연결**: GitHub Actions와 자연스럽게 연동된다. 이슈 생성 → Actions 트리거 → 에이전트 실행이 하나의 흐름이다

## 1인 기업의 인프라 결정 원칙

이 전환을 통해 하나의 원칙을 명문화하게 됐다.

> _이미 쓰고 있는 도구의 기능을 최대한 활용하라. 새 인프라는 기존 도구가 진짜 한계에 부딪혔을 때만 도입한다._

1인 기업은 리소스가 한정되어 있다. 도구를 추가할수록 유지 비용과 컨텍스트 전환 비용이 쌓인다. 파일 기반에서 GitHub Issues로의 전환은 단순한 기술 교체가 아니라, "우리가 이미 가진 것으로 최대한 멀리 가자"는 운영 철학의 반영이다.

이 원칙은 이후 모든 인프라 결정의 기준이 되었다.

## 클라우드로 확장하기

로컬에서 수동으로 에이전트를 실행하는 건 한계가 있다. 내가 자고 있는 동안에는 아무것도 안 돌아간다.

해결책은 **Git + GitHub Actions**다.

```
CEO가 Issue 생성
    → GitHub Actions가 라벨로 수신 에이전트 식별
    → 해당 에이전트 자동 실행
    → 결과를 Issue 댓글로 보고
    → 이슈 닫기로 완료 처리
```

현재 진화 단계:

```
[1단계] 로컬 파일 기반 + 독립 AI 에이전트 세션
[1.5단계] Git + GitHub Actions (클라우드 자동화)  ← 현재
[2단계] 자주 쓰는 패턴을 스킬/자동화로 정리
[3단계] Agent SDK로 실시간 자동화
```

아직 1.5단계다. 하지만 이 글을 쓰는 것 자체가 이 시스템으로 처리되고 있다는 점이 재미있다.

## 다음 편 예고

다음 편에서는 경영기획실장 에이전트를 실제로 만들어보는 과정을 다룬다. `AGENT.md`로 에이전트 페르소나를 정의하는 방법, 그리고 처음 설계한 것과 실제 운영 사이에서 무엇이 바뀌었는지를 솔직하게 공유할 예정이다.
